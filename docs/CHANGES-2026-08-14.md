## 1. Closed-invoice transmit to Velocity
Deploys: 20260814-123117, 20260814-124003

**Problem.** ECI-025300 was paid in Sage but never reached Velocity, so the lockbox
payment could not be applied there. The transmit picker offered only open receivables.

**Files and changes.**
- `sage.js`: new `getInvoicesByIds(invoiceIds)`. Queries ARINVOICE by RECORDID in
  chunks of 40 with NO open-balance filter, returning recordNo, invoiceId, customer,
  dates, totalEntered, totalDue, and STATE (verified live: ECI-025300, L&A - 7132
  Daniels Drive, $2,766.54, state Paid).
- `app.js` `/api/velocity/pending`: made async; with `includeClosed=1` and a range
  under 100 numbers, any number missing from the open cache is looked up in Sage
  directly (prefix-padded: S- 4 digits, others 6). Closed rows carry `closed: true`,
  Balance $0, full Amount Paid, and normal LOC1/LOC2 classification.
- `app.js` `/api/velocity/transmit`: accepts `includeClosed: true` (must be explicit
  in the POST body; the preview checkbox state is passed through). Closed rows are
  filtered by target line like open ones. High-water marks unaffected: they still
  advance only on confirmed Velocity acceptance, and below-mark or retransmit sends
  never move them.
- `public/comms.js` (v20260814c): "include closed/paid (for payment application)"
  checkbox in the InterNex picker; amber "CLOSED - for payment application" badge on
  those rows; empty-preview help text now points to the checkbox instead of saying
  closed invoices can never be sent.

## 3. Velocity login failure: diagnosis and partial fix
**Finding.** First live batch (ECI 25431-25447, 17 invoices) failed at Auth0 login.
Nothing was transmitted; the batch is safe to re-run. Root cause: macOS releases the
keychain secrets only to GUI-session processes. SSH-invoked runs get exit 36 from
`security find-generic-password -w` (item exists; metadata reads fine; secret does
not). The nightly scraper and OpenClaw work because they run inside the login
session. Every earlier portal run was a dry-run, which never authenticates, so this
surfaced only on first live send.

**Change made.** iMac `velocity-uploader.js` getCreds now names the keychain path
explicitly (`~/Library/Keychains/login.keychain-db`), matching the scraper. Backup:
`velocity-uploader.js.bak-keychain-20260814`. Correct but not sufficient.

**Open item (Edwin).** Re-add the two entries with `-A` (or `-T /usr/bin/security`)
from the iMac GUI session, then re-run the batch:
```
security add-generic-password -U -A -s com.ecf.openclaw -a ecf-internex-email -w "<email>"
security add-generic-password -U -A -s com.ecf.openclaw -a ecf-internex-password -w "<password>"
```

## 4. EDI preflight headroom excludes tax
Deploy: 20260814-124003

**Problem.** Preflight compared the tax-inclusive invoice total against PO headroom
(ECI-025448: $21,154.95 vs $19,957.50 headroom, false overage warning). Amazon funds
POs on the pre-tax subtotal; tax rides on top.

**Change** (`public/index.html`). `renderEdiPreflight(recordNo, x12)` parses total
tax from the generated 810's TXI segments; the checklist re-renders after the 810
arrives; the headroom compare uses the pre-tax amount and says so explicitly
("$19,957.50 pre-tax invoice (tax $1,197.45 rides on top, not charged to PO funds)").
The queue-level overage flag still uses the tax-inclusive total (tax is unknown
until an 810 is generated); the preview is the authoritative check.

## 5. Permanent PO consumption ledger
Deploys: 20260814-152043, 20260814-152107, 20260814-152343

**Problem (Edwin's 2D-20620291/BOS3 case).** Consumed was recomputed from the live
payee feed on every read. Paid invoices age off Payee Central, so their draw was
forgotten: portal showed 11 invoices/$1,861,404 while Amazon's Matched-invoices tab
held 14/$1,926,339. The $64,935 gap was exactly the three Paid invoices (AST001814
$15,300, S7303 $835, S9005 $48,800). The row's Available column was already correct
because it displays Amazon's own scraped figure; consumed and the computed available
were fiction. Sweep found 303 POs diverged the same optimistic direction.

**Design rules (per Edwin).** A match is permanent. Only an observed
Rejected/Cancelled/Cancellation-in-Progress transition releases funds (and a
returning invoice re-charges). Consumption only grows automatically; any decrease
requires manual confirmation.

**Files and changes.**
- `po-ledger.js`:
  - New tables (created lazily): `po_consumption` (UNIQUE po+invoice, amount,
    status_last, source feed|amazon-implied|manual, first/last_seen, released_at,
    released_reason) and `po_consumption_review` (kind, detail, proposed_delta,
    resolved_at/by/resolution).
  - `syncConsumptionFromIndex()` (throttled 5 min): upserts every payee-index item
    (index KEY is the invoice number). Inserts new matches; raises amounts; releases
    on non-consuming statuses; un-releases on return; queues amount decreases for
    review instead of applying. Never deletes. Manual BEGIN/COMMIT (db.getDb() is
    not better-sqlite3; no .transaction()).
  - `buildConsumedByPo()` now reads the ledger (SUM where released_at IS NULL),
    reporting invoiceCount (named rows) and backfillAmount separately.
  - `getConsumptionRecon()`: three-way compare per PO of ledger consumed vs Amazon
    implied consumed (poAmount - Available). Buckets: ok, autoFixable, overLedger,
    noAmazonFigure, overdrawn.
  - `runConsumptionBackfill()`: one adjustment row per PO, invoice "(pre-feed
    history)", source amazon-implied, targeted to Amazon's implied figure. Only
    raises consumption automatically; auto-shrinks ONLY its own adjustment row as
    named feed rows appear (re-attribution, floored at $0); residual excess is
    queued for review. Idempotent (second pass: 0 changes).
- `app.js` routes:
  - GET `/api/po/consumption-recon` (finance.view)
  - POST `/api/po/consumption-backfill` (po.admin, audited)
  - GET `/api/po/consumption-reviews` (finance.view)
  - POST `/api/po/consumption-review/:id/resolve` (po.admin, audited): resolution +
    optional negative applyDelta writes a "(manual adjustment)" row; the ONLY path
    that shrinks consumption.

**Backfill results (all 1,179 ledger POs; 1,120 with an Amazon figure).**
- 761 POs reconcile to the dollar.
- 31 over-drawn per Amazon (negative Available). Each likely holds an unfunded
  invoice: on 2D-20620291 the other 13 invoices sum EXACTLY to the $1,866,595 PO
  value, so AST002251 ($59,744, In Progress) is entirely unfunded and will hold
  until Amazon adds funds.
- 387 POs have consumption but no Amazon figure (masked or never scraped): watch-list.
- 359 in review queue, ledger > Amazon implied. Hypothesis: feed "Invoice Amount" is
  tax-inclusive while Amazon matches pre-tax (same tax-rides-on-top behavior as the
  EDI fix). Deliberately untouched; stage 2 resolves them with authoritative data.
